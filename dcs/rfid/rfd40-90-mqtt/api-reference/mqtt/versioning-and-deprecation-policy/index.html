Versioning and Compatibility

Reference·Audience: API consumer·Use: judge whether a contract update can affect your integration, and find what is deprecated

The MQTT API is defined by one AsyncAPI contract. This page explains how that contract's version changes and how it marks fields and values that you should stop using.

The Contract Version​

PropertyValue
TitleZebra Handheld RFID Reader (RFD40/RFD90) IoT Connector API
Identifierurn:com:zebra:iotc:rfd40-90:mqtt
Version1.26.0
FormatAsyncAPI 3.0.0, with payloads in the AsyncAPI Schema Object, a superset of JSON Schema Draft 07
Default content typeapplication/json

The contract version is not the apiVersion that a reader reports in a reply. See API Version Support.

What a Minor Version May Change​

The contract states no versioning policy. The minor versions recorded so far, 1.23.0 through 1.26.0, were additive or relaxing: nothing that a conforming client sent against the previous minor version became invalid. They:

  • admitted values that an earlier version rejected, for example a new enumeration member in a reply;
  • stopped requiring members that an earlier version required;
  • added optional members, bounds on previously unbounded fields, or documentation.

Two consequences follow for your integration:

  • Check generated values against new bounds. When version 1.23.0 bounded previously unconstrained fields, such as tenantId at 48 characters, no published example became invalid, but a value your code generates might have.
  • Replies and events can contain values your code has not seen. If you validate reader traffic against the contract, validate against the latest minor version.

What a major or patch version may change is not specified in the available sources.

Where Changes Are Recorded​

The contract carries no change history. The Changelog records what changed in each contract version.

How Deprecation Is Stated​

The contract uses no deprecation keyword or extension: no member is marked deprecated, and no value is marked as an alias. Where a member is being retired, its description says so. Reserved and Deprecated Fields lists the members to stop relying on, the reserved members that have no effect, and the unsupported values.

A deprecation notice period, a removal schedule, and the version in which a deprecated item is removed are not specified in the available sources.

Names Removed from the Contract​

The command names set_eth, cloud_connect, and config_alerts are no longer part of the contract. No message in version 1.26.0 carries them, and the contract describes no way to configure the Ethernet interface.

API Version Support​

Four version identifiers appear in the MQTT API. They measure different things, so check which one a question needs before you rely on it.

Version Identifiers​

IdentifierWhere it appearsWhat it identifies
Contract version, currently 1.26.0The AsyncAPI contract's info.versionThe published message contract that this reference describes. See Versioning and Compatibility.
apiVersionCommand responses (not declared on delete_wifi_profile) and mqttConnEVTThe version reported by the command handler that produced the reply. See API Version Reporting.
readerVersion.detailedVersions.iotcVersionThe get_version responseThe IoT Connector version on the reader.
readerVersion.firmwareVersionThe get_version responseThe reader firmware build.

Values an apiVersion Can Take​

Command responses carry apiVersion as a string from this set: V1.0, V1.1, V1.2, V1.21, V1.22. mqttConnEVT carries it as a JSON number, such as 1.21; its schema pairs type: number with the same string set, which no number can match. The full rules are on Enumerations.

What a Version Cannot Tell You​

  • Per-operation support. The contract declares one set of apiVersion values for every command. It does not state which version each command handler reports, or which operations each version supports. The Details section of each operation page shows an API version for that command; because the contract declares no per-command version, treat that value as informational, not as a constraint to validate against.
  • Ordering. Don't compare apiVersion strings to decide which is newer. The contract defines no ordering for them.
  • Firmware mapping. Which firmware build reports which apiVersion or iotcVersion is not specified in the available sources.
