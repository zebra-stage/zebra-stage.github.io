control_operation

Reference·Audience: API consumer·Use: start or stop the RFID radio (or the scanner) on demand

Overview​

control_operation starts or stops a reader subsystem on demand. You pick a controlType (RFID — the radio inventory engine, or SCANNER — the barcode scanner) and an operation (START or STOP). For RFID, START begins an inventory cycle using the currently configured operating mode and the device streams tag reads as dataEVT events until you STOP (or the operating-mode stop conditions are met). It is a state-changing control-plane (CTRL) command, and it is reversible — a START is undone by a STOP.

This is a CTRL-endpoint command, published on the control endpoint (<tenantId>/CTRL/clients/cmnd/<serial>) and answered only there (not on the MGMT/MDM channel). Returning a response requires an active CTRL endpoint (config_endpoint, epType: CTRL, activate: true). Receiving the tag stream that START triggers also requires an active DATA1 endpoint (<tenantId>/DATA/clients/data1event/<serial>; see the data endpoint topic mapping).

A START executes whatever the operating mode has armed — including destructive access operations. See the danger callout in Notes and Caveats.

When to Use​

Use control_operation to drive the radio (or scanner) on demand:

  • Start an inventory — controlType: RFID, operation: START begins reading tags with the current operating mode; the device streams dataEVT events over the DATA endpoint.
  • Stop an inventory — operation: STOP halts the radio; the tag stream ceases.
  • Control the scanner — controlType: SCANNER starts / stops the barcode scanner instead of the radio.

Configure how the reader reads with set_operating_mode first, then START — control_operation itself has no tuning parameters. If the inventory state is uncertain, check it with get_status before sending START.

Topic Mapping​

control_operation is the one command that drives both planes: the command travels over CTRL, while the device publishes the tag events a START triggers over DATA.

PlaneMessageDirectionTopicNote
CONTROLRequestApp → Reader<tenantId>/CTRL/clients/cmnd/<serial>On the control endpoint. Requires an active CTRL endpoint.
CONTROLResponseReader → App<tenantId>/CTRL/clients/resp/<serial>Correlated reply; the in-payload requestId links the twin topics.
DATAEventReader → App<tenantId>/DATA/clients/data1event/<serial>The dataEVT stream a RFID START triggers. Requires an active DATA1 endpoint to receive it.

Topics follow the pattern <tenantId>/<topic>/<serial> — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example RFD40-212735201D0053). App → Reader means your app publishes and the reader subscribes; Reader → App means the reader publishes and your app subscribes.

The command is answered only on the CTRL endpoint; the tag stream is published on the DATA1 endpoint's configured publish topic (data1event by default). DATA2 is currently not supported.

See Topics and Channels.

Key Fields​

  • ctrlOprPayload.controlType (request) — RFID (radio inventory engine) or SCANNER (barcode scanner).
  • ctrlOprPayload.operation (request) — START (begin) or STOP (halt).
  • response.code (response) — read this to determine success vs failure. The contract requires it; note the reported success-path omission (see Success without a code). See Response Codes.

Request Semantics​

Modes. ctrlOprPayload.operation selects the action for the chosen controlType:

  • START — begin the operation. For RFID, this starts an inventory cycle using the current operating mode and streams dataEVT events over the DATA endpoint.
  • STOP — halt the active operation. For RFID, the tag stream ceases (a single in-flight read may still be flushed shortly after — see Notes).

A STOP when no operation is active returns code 12 ("No Radio Operation in Progress") — this is not a failure, the device is already idle. A START while an inventory is already running returns code 11 ("Inventory in progress").

  • SCANNER uses the same request envelope as RFID. ctrlOprPayload declares one controlType (RFID | SCANNER) and one operation (START | STOP), both required, with no scanner-specific field and no separate payload — a scanner request differs from an RFID request only in the controlType value. Decoded barcodes are declared on the DATA plane, not in this command's response: the dataEVT data object carries barcodeData[] (decodedBarcode, plus symbology, the barcode type as a hexadecimal string such as 0x03) alongside tagData[]. Codes 11 and 12 above are radio-scoped — the contract describes them as an RFID inventory already running and no radio operation active — and the schema defines no scanner-specific response code, leaving code 23 for a controlType or operation outside its enum. Physical-trigger behavior and per-model scanner coverage are outside the schema and are not documented here — see Scan Barcodes.

Response Codes​

control_operation returns response.code. The codes applicable to this command are below; for the full table see the Response Codes and Correlation and Request/Response Pairing.

CodeDescription
0Success — the radio (or scanner) started or stopped. (Readers have been reported to omit code on this reply — see above.)
11Inventory in progress (IOT_ERROR_INVENTORY_IN_PROGRESS) — a START was sent while an RFID inventory is already running. Stop the current inventory first; if the state is uncertain, check get_status.
12No Radio Operation in Progress (IOT_ERROR_NO_RADIO_OP_IN_PROGRESS) — a STOP was sent while the radio is already idle. Not a failure — no action required. Unique to this command.
23Invalid enum value (IOT_ERROR_INVALID_ENUM) — controlType or operation is outside its allowed set.
101Default error — generic catch-all.

Notes and Caveats​

Armed access operations execute on START

control_operation has no tuning parameters; a START runs whatever set_operating_mode last configured. If destructive access operations (WRITE / LOCK / KILL) are armed, START executes them on every tag in range — KILL and PERMANENT_LOCK are irreversible. Confirm the operating mode is read-only (no armed accessOperations) before starting a production inventory. See set_operating_mode § Notes and Caveats.

  • START drives two planes; the tag stream requires a DATA endpoint. The command round-trip is on the CTRL endpoint, but the tag reads a RFID START produces are published as dataEVT events on the DATA endpoint (<tenantId>/DATA/clients/data1event/<serial> for DATA1_EP). To receive them, a DATA1 endpoint must be active — activate one with config_endpoint. dataEVT.type echoes the active operating-mode profile, and the mode's tagMetaDataToEnable flags gate which tagData fields appear (EPCid is always present).
  • STOP is immediate at the radio, but a trailing read may still flush. A STOP stops the radio right away, yet a single in-flight / buffered read may still be delivered on the DATA plane a couple of seconds after the STOP (≈2.9 s observed on RFD40) before the stream fully ceases. Do not treat one trailing dataEVT after a STOP as continued inventory.
  • Configure the mode before you START. Set profiles, power, triggers, select filters, and access operations with set_operating_mode first, then START; control_operation itself sets none of these. The operating mode is volatile: it resets to the default (BALANCED_PERFORMANCE, no armed access operations) on reboot, so re-apply it after a reboot before starting.

control_operation is reversible (START ↔ STOP) and carries no credentials — the tag EPCid values in the resulting dataEVT stream are identifiers read off physical tags, not secrets. SCANNER control follows the same request/response shape as RFID (verified paths are RFID START/STOP on RFD40). For the concept-level view, see Start and Stop Inventory.
