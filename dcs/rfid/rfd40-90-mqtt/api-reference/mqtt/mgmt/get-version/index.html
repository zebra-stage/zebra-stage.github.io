get_version

Reference·Audience: API consumer·Use: read the reader's identity and software versions

Overview​

get_version retrieves the reader's identity and software-version metadata in a single round trip: model, serial number, SKU, top-level firmware version, and a component-level breakdown (scanner, radio, and IoT Connector versions). It is a read-only query on the device-management (MGMT) endpoint — the app publishes the command and the device publishes a correlated reply containing the readerVersion object.

Because it is idempotent, read-only, and independent of radio state, get_version can be issued at any point once the connection is active, and it is the natural first command to send after any connect, reconnect, or bootstrap — to confirm which device you are talking to and which command set it supports. Where get_version reports identity, get_status reports live runtime health.

When to Use​

Use get_version when you need to establish device identity and the software baseline — typically in a management or fleet workflow over the MGMT endpoint. It answers "is this the device I expect, and what command set does it support?"

  • Identify the device: readerVersion.model, serialNumber, and sku confirm the exact model and regional/hardware variant, and key asset-tracking, support tickets, and device registration to the physical label.
  • Gate on firmware / capabilities: compare readerVersion.firmwareVersion and detailedVersions against your expected baseline before an update or when diagnosing an issue; read detailedVersions.iotcVersion to decide which MQTT API commands and features are available.
  • Confirm a firmware update applied: set_os returns only an accepted acknowledgment (code 1) with no terminal success/failure on the response topic — poll get_version.readerVersion.firmwareVersion to verify the new firmware actually took effect.

Topic Mapping​

MessageDirectionTopicNote
RequestApp → Reader<tenantId>/MGMT/clients/cmnd/<serial>On the management endpoint.
ResponseReader → App<tenantId>/MGMT/clients/resp/<serial>Correlated reply to the request above; the in-payload requestId links the twin topics.

Topics follow the pattern <tenantId>/<topic>/<serial> — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example RFD40-212735201D0053). App → Reader means your app publishes and the reader subscribes; Reader → App means the reader publishes and your app subscribes.

Credentials are presented once at CONNECT. The requestId you send is echoed in the response so you can pair reply to request. The endpoint's mqttParams govern QoS and retain, not this command.

See Topics and Channels.

Key Fields​

  • requestId (request) — your correlation token; make it unique per request. The device echoes it in the response so you can pair reply to request.
  • readerVersion.model (response) — RFD40 or RFD90; branch model-specific configuration on it.
  • readerVersion.firmwareVersion (response) — the reader firmware build; compare against your baseline and use it to confirm a set_os update applied.
  • readerVersion.detailedVersions.iotcVersion (response) — the IoTC version, which determines the available command/feature set.
  • response.code (response) — read this to determine success vs failure (see Response Codes).

Response Payload​

The response envelope is command, requestId, apiVersion, response, and a readerVersion object. On the Schema tab, expand readerVersion (and its detailedVersions sub-object) to see every field — its type, whether it is required, its enum/units, an example value, and a description; the Example tab shows the full JSON. readerVersion is optional at the envelope level, but when it is present its six identity members (firmwareVersion, model, serialNumber, sku, companyName, manufacturerName) are all required; detailedVersions and its members are optional.

Response Semantics​

  • Version fields. Use readerVersion.detailedVersions.iotcVersion as the IoTC software version, and compare firmware builds via readerVersion.firmwareVersion. The envelope apiVersion is per-handler — see API Version Reporting.
  • iotcVersion can be newer than its enum. The contract's example reports V1.22, but the field's enum lists only V1.1, V1.2 and V1.21, so the contract's own example does not validate against it — a known issue in the source schema. Parse iotcVersion as a string and compare versions numerically rather than rejecting an unlisted value.
  • companyName and manufacturerName are constrained to Zebra Technologies. readerVersion.detailedVersions is optional and may be absent on some builds; the example values shown (firmware, SKU, serial) are illustrative — real values vary by unit and region.

Response Codes​

get_version returns response.code. The codes applicable to this command are below; for the full table see the Response Codes and Correlation and Request/Response Pairing.

Examples​

get_version is a single request/response exchange. Publish the standard {command, requestId} request shown under Request Payload; the device replies on the response topic with the correlated reply — the requestId you send (abc123) is echoed back so you can pair reply to request. The full reply, field by field, is shown under Response Payload above.

Notes and Caveats​

  • Confirming a firmware update: set_os returns an acceptance response only — code 1 ("Command payload is accepted") on the response topic, with no terminal success or failure. While the update runs, the reader emits live progress events: a FIRMWARE_UPDATE alert carrying alertDetails.fwUpdateStatus (updateStatus, overallProgress, stage), provided firmware-update events are enabled with config_events (eventConfiguration.firmwareUpdate: true). To confirm the update applied, watch those events, or poll get_version and check that readerVersion.firmwareVersion advanced to the expected build.

get_version is idempotent and independent of radio state, so it can be issued at any time on an active connection and is the right first command after any connect, reconnect, or bootstrap — confirm the device identity and IoTC version before relying on newer commands or fields. See The Configuration Model.
