get_status

Reference·Audience: API consumer·Use: request an on-demand device-health snapshot

Overview​

get_status retrieves a point-in-time health and status snapshot of the reader. It is a read-only query on the device-management (MGMT) endpoint: the app publishes the command and the device publishes a correlated reply containing power, radio, clock, terminal-link, and battery information under deviceStatus.

Because it is read-only, get_status is safe to call at any time. It complements the asynchronous heartBeatEVT push: heartBeatEVT carries only a lightweight inventory-status or battery-alert summary, so use the event stream for continuous monitoring and get_status for an immediate, full snapshot.

When to Use​

Use get_status when you need an immediate, correlated snapshot of reader health — power source, radio activity/connection, system clock, terminal link, and battery condition — typically in a management workflow over the MGMT endpoint. It confirms device state on demand rather than waiting for the next asynchronous heartbeat.

  • Get: the current deviceStatus snapshot (power, radio, clock, terminal connection, battery).
  • Use it for: pre-flight safety checks before a state-changing command, spot health checks, and diagnostics. (deviceStatus.radioActivity in the response reports the activity status of the device's radio — see Key Fields.)
  • Prefer a different command when: you want continuous monitoring rather than a single read — subscribe to heartBeatEVT instead for periodic pushes, though it carries only an inventory-status or battery-alert summary, not the full power/radio/clock/terminal/battery snapshot get_status returns.

Topic Mapping​

MessageDirectionTopicNote
RequestApp → Reader<tenantId>/MGMT/clients/cmnd/<serial>On the management endpoint.
ResponseReader → App<tenantId>/MGMT/clients/resp/<serial>Correlated reply to the request above; the in-payload requestId links the twin topics.

Topics follow the pattern <tenantId>/<topic>/<serial> — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example RFD40-212735201D0053). App → Reader means your app publishes and the reader subscribes; Reader → App means the reader publishes and your app subscribes. To watch a whole fleet rather than one reader, put the MQTT single-level wildcard + in the serial slot — <tenantId>/MGMT/clients/resp/+ — as explained under Topics and Channels.

Credentials are presented once at CONNECT. The requestId you send is echoed in the response so you can pair reply to request. The endpoint's mqttParams govern QoS and retain, not this command.

Key Fields​

  • requestId (request) — your correlation token; make it unique per request. The device echoes it in the response so you can pair reply to request.
  • deviceStatus.radioActivity (response) — the activity status of the device's radio (INACTIVE / ACTIVE).
  • deviceStatus.powerSource (response) — how the reader is currently powered (WALLCHARGER / USB / CRADLE, the contract's enum); current firmware has also been reported to return NONE, which the enum does not allow.
  • response.code (response) — read this to determine success vs failure (see Response Codes).

The response envelope is command, requestId, apiVersion, response, and an optional deviceStatus snapshot. Response Semantics​

  • Which deviceStatus fields appear depends on device state and model — absent fields are normal behavior, not an error. Note that deviceStatus reports two distinct temperatures: deviceStatus.temperature (device) and deviceStatus.batteryStatus.temperature (battery) — do not conflate them.
  • The reader has no RTC backup battery. After a cold start or factory reset, systemTime starts at a baseline default; the device syncs its clock from network time once it has a network connection. There is currently no API to change the NTP configuration — set the NTP server details (and, if NTP is unreachable, the device time itself) from the 123RFID Desktop application. Time-sensitive operations (TLS certificate validity, log/event timestamps) may use the default time until the clock has synced.
  • stateOfHealth is one grade, on two surfaces. deviceStatus.batteryStatus.stateOfHealth here and the batteryAlert.stateOfHealth carried by alerts and heartBeatEVT use the same enum — GOOD / CRITICAL / MODERATE — so shared battery logic needs no conversion. Keep it distinct from the event's status, which is a charge band (LOW / CRITICAL / CHARGING / FULL / HIGH), not a health grade. See Interpret stateOfHealth.
  • ntp.offset and ntp.reach are not reported by the reader. The schema declares both fields; the values on the Schema tab (120 and 321) are the schema's own field examples, and the contract's message example shows 0 for each. Current firmware has been reported not to populate either one, so treat their absence as normal and do not build clock-health logic on them. Removing them from the schema is an upstream request to the API owners; until then the fields remain declared.

Response Codes​

get_status returns response.code. The codes applicable to this command are below; for the full table see the Response Codes and Correlation and Request/Response Pairing.

CodeDescription
0Success — status retrieved and returned.
3Not able to retrieve information — the reader could not gather the requested status at this moment. Retry; if persistent, reboot after stopping any active inventory.
101Default error — generic catch-all.

Examples​

get_status is a single request/response exchange. Publish the standard {command, requestId} request shown under Request Payload; the device replies on the response topic with the correlated reply — the requestId you send (abcd123) is echoed back so you can pair reply to request. The full reply, field by field, is shown under Response Payload above.

Notes and Caveats​

  • get_status is the on-demand poll; heartBeatEVT and related alerts push a lighter periodic summary (an inventory-status or battery-alert block), not the full get_status snapshot. Prefer the events for continuous monitoring and get_status for a complete point-in-time check. Cross-command apiVersion reporting can differ (for example mqttConnEVT emits a numeric apiVersion); that is a firmware note, not a get_status schema difference.
