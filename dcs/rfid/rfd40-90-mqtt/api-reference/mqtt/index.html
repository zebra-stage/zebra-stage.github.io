MQTT API

The MQTT API is the interface that the IoT Connector, the firmware on RFD40 and RFD90 readers, provides for managing a reader, controlling RFID inventory, and receiving events and tag data. Every exchange travels over MQTT 3.1.1 through a broker that you operate. This reference describes version 1.26.0 of the API contract.

Who Takes Part​

An exchange involves up to five parties. The reader and your applications never address each other directly: each is an MQTT client of the same broker.

PartyRole in the MQTT API
Reader (RFD40 or RFD90)The hardware. It holds the endpoint configuration that tells the IoT Connector which broker to use.
IoT ConnectorThe firmware on the reader. For each active endpoint, it opens its own MQTT client session to the broker named in that endpoint. Depending on the endpoint type, it subscribes to the endpoint's command topic and publishes responses, events, connection state, or tag data.
BrokerYour MQTT 3.1.1 broker. It relays messages between the reader and your applications. The broker address is part of the reader's endpoint configuration; the API has no default broker. If the reader's session ends without a clean disconnect, the broker publishes the Last Will that the reader registered when it connected.
Host applicationThe application that controls the reader. It publishes commands to the reader's command topic and subscribes to the response topic, pairing each reply with its request by requestId.
Consuming applicationsApplications that subscribe to events, connection state, and tag data. A consuming application can be the host application or a separate service. Tag data arrives on a DATA1 endpoint; DATA2 is currently not supported.

123RFID Desktop enters the reader's first endpoint configuration during bootstrap. Later endpoints can be added over MQTT with config_endpoint.

How Messages Flow​

Host application     -- commands ---->   Broker   -- commands ---->   Reader (IoT Connector)
Host application     <-- responses ---   Broker   <-- responses ---   Reader (IoT Connector)
Consuming app        <-- events ------   Broker   <-- events ------   Reader (IoT Connector)
Consuming app        <-- tag data ----   Broker   <-- tag data ----   Reader (IoT Connector)
Consuming app        <-- Last Will ---   Broker

The flow shows who publishes and who subscribes, not a network path. Events include the CONNECTED form of mqttConnEVT; the broker publishes the DISCONNECTED form as the reader's Last Will. A host application can also subscribe to events and tag data. The contract describes the IoT Connector on readers connected over Wi-Fi and Ethernet; which interface carries a given session is not specified in the available sources.
