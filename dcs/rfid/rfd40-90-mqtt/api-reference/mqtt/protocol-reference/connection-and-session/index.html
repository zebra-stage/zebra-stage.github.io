Connection and Session

Reference

The reader, not your application, opens the MQTT connection that carries its traffic. You describe that connection in an endpoint configuration on the reader: the broker address, the transport, the credentials, the certificates, and the topics. This page covers the connection and its session; TLS and Authentication covers encryption and credentials.

The Connection Path​

  1. Bootstrap. 123RFID Desktop enters the reader's first endpoint configuration.
  2. Configure. More endpoints can then be added or changed over MQTT with config_endpoint, and read back with get_endpoint_config.
  3. Connect. For each active endpoint, the IoT Connector opens an MQTT 3.1.1 session to the configured broker and registers its Last Will.
  4. Announce. When the session is established, the reader publishes a CONNECTED mqttConnEVT on the endpoint's connection-state topic. See Topic Slots for the endpoint types that carry it.
  5. Exchange. Your applications connect to the same broker, subscribe to the reader's topics, and publish commands.

Broker Connection​

The reader opens its own MQTT sessions to your broker. Each session belongs to an endpoint: a named connection configuration stored on the reader. This section describes what an endpoint connects to and how its session behaves over time.

Protocol Version​

The contract declares MQTT 3.1.1. The endpoint configuration has no field that selects a different protocol version.

The reader reports the protocol version of each session in the mqttVersion field of mqttConnEVT. The field is a number, which current firmware sends as 3.0999999. Don't compare it with 3.1 for equality.

Whether the reader supports any other MQTT version is not specified in the available sources.

Endpoints​

An endpoint is a named configuration of the reader's MQTT client for one broker session. You manage endpoints with config_endpoint and read them back with get_endpoint_config.

  • The name identifies the endpoint. endpointName holds up to 15 characters, per Zebra's release notes; the contract states no limit. Together with epType, it selects the endpoint that an update or delete changes.
  • Only an active endpoint connects. The reader makes a connection for an endpoint only when activate is true. The default is false.
  • A reader can hold several endpoints. Endpoints can point at the same broker or at different brokers, so management, control, and tag-data traffic can be split across brokers.
  • Endpoints survive a reboot. After a reboot, saved and active endpoints are restored, and the reader reconnects to the broker it was connected to.

All endpoint fields, with their types and defaults, are listed in MQTT Endpoints.

Endpoint Types​

epType sets the class of traffic that an endpoint carries.

epTypeTraffic
MGMTManagement commands, their responses, and management events
MGMT_EVTManagement events on a separate endpoint
CTRLRFID control commands and their responses
DATA1Tag and barcode data, first data channel
DATA2Tag and barcode data, second data channel. Currently not supported
MDMA mobile-device-management form of the management endpoint
SOTIA mobile-device-management form of the management endpoint, used by the SOTI integration, which this reference does not cover

The contract does not include an example of a MGMT_EVT, DATA2, or SOTI endpoint. DATA2 is currently not supported.

The operation pages in this reference place management commands on the management endpoint and control commands on the CTRL endpoint. Whether an endpoint accepts commands outside its type is not specified in the available sources.

Which topic carries which traffic depends on the position of each topic in the endpoint configuration. See Topic Slots.

Broker Address, Port, and Transport​

FieldWhat it sets
urlThe broker address. Every published example is a bare host name or IPv4 address with no scheme, and the port is set separately. Treat the value as a host, not as a full URI.
portThe broker's TCP port, from 1 to 65535.
protocolMQTT for a plaintext connection, or MQTT_TLS for a TLS connection. See TLS and Authentication.

The contract uses port 1883 for plaintext MQTT and 8883 for MQTT over TLS, and advises TLS on any untrusted network. The reader does not check that protocol and port match: an endpoint with protocol: MQTT and port: 8883 is accepted and then fails to connect.

Session Lifecycle​

  1. Connect. For each active endpoint, the reader sends an MQTT CONNECT packet with its client ID, its credentials if any, its keep-alive interval, and its clean-session flag. See Connection Parameters.
  2. Register the Last Will. In the same CONNECT packet, the reader registers a Last Will: the DISCONNECTED form of mqttConnEVT, which carries no timestamp. See Last Will.
  3. Announce the connection. When the session is established, the reader publishes a CONNECTED mqttConnEVT with a timestamp on the endpoint's connection-state topic. The contract says every active endpoint does this, but its topic-slot table lists mqttConnEVT only for MGMT, MDM, and CTRL endpoints; see Topic Slots.
  4. Lose the connection. If the session ends without a clean MQTT disconnect, for example because the broker receives nothing within one and a half keep-alive intervals, the broker publishes the Last Will. A clean disconnect suppresses the Last Will. Whether the reader publishes anything when it disconnects cleanly is not specified in the available sources.
  5. Reconnect. The reader waits between reconnectDelayMin and reconnectDelayMax seconds before it reconnects. How the delay grows between those limits is not specified in the available sources.

The order in which the reader subscribes to its command topic and announces the connection is not specified in the available sources.

Confirming a Connection​

Each signal answers a different question:

SignalWhat it shows
A CONNECTED mqttConnEVTA new session was established for that endpoint. On its own, it does not show that the reader restarted, because a network reconnect produces the same message.
A DISCONNECTED mqttConnEVTThe broker published the Last Will because the session ended without a clean disconnect. Because the broker detects the loss through keep-alive, the message can arrive some time after the connection was lost.
No DISCONNECTED messageNothing. A clean disconnect suppresses the Last Will, so the absence of a DISCONNECTED message does not mean the reader is connected.
The endpoint listed under activeEndpoints in get_endpoint_configThe reader stores the endpoint as active.
A reply to a command sent on the endpointThe endpoint's session is up, and the reader is processing commands on it.

For ongoing liveness monitoring, use heartBeatEVT; see Reader Availability.

Changing an Endpoint​

  • A reply is not a connection. A config_endpoint reply with code 0 means that the reader accepted the configuration. Confirm the connection with the signals above.
  • Active endpoints can refuse changes. config_endpoint returns code 35 when you modify an endpoint that is active; the recommended action is to deactivate the endpoint first. How to deactivate an endpoint without modifying it is not specified in the available sources.
  • You can cut off your own session. Changing the broker url, port, or protocol of the endpoint that carries your command session, or deleting that endpoint, can sever the session you are using. Adding an endpoint of a different type does not affect it.

The full list of codes that config_endpoint can return is in Codes by Command.

Connection Parameters​

These fields control how the reader's MQTT client behaves for one endpoint. They sit in the endpoint's configuration object and in its configuration.mqttParams object, which you send with config_endpoint. Complete type information for every field is in MQTT Endpoints.

Required Fields When You Add an Endpoint​

The contract requires the same seven fields in configuration for every config_endpoint operation: endpointName, epType, protocol, activate, url, verificationType and port. Its own delete example sends only endpointName and epType, and its update example omits verificationType and port; see config_endpoint.

qosCommon and tenantId are optional. What the reader uses when you omit them is not specified in the available sources; in the reader's default endpoint configurations, the tenant ID is empty and every topic uses QoS 0.

Session Fields​

FieldLimitsIf omittedWhat it controls
mqttParams.clientIdNone in the contractNot specifiedThe client identifier the reader sends in its CONNECT packet
mqttParams.keepAliveUp to 65535 secondsNot specifiedThe longest interval the reader allows between its own control packets
mqttParams.cleanSessiontrue or falsetrueWhether the broker discards the reader's previous session when it connects
mqttParams.reconnectDelayMinSeconds; none in the contractNot specifiedThe shortest wait before the reader reconnects after losing the connection
mqttParams.reconnectDelayMaxSeconds; none in the contractNot specifiedThe longest wait before the reader reconnects
activatetrue or falsefalseWhether the reader connects for this endpoint at all

The contract's server description uses a keep-alive of 300 seconds, and its config_endpoint examples send 300. Its get_endpoint_config read-back examples report 96, which is also the keep-alive in the reader's default endpoint configurations. The contract states no default.

Client ID​

  • Portability. MQTT 3.1.1 guarantees only that a broker accepts client IDs of 1 to 23 characters from 0-9, a-z, and A-Z. A longer ID, or one that contains ., _, :, or -, works only on brokers that allow it.
  • Empty client ID. An empty clientId is valid only with cleanSession: true. MQTT 3.1.1 requires a broker to reject an empty client ID combined with a persistent session, and a broker may reject an empty client ID in any case.
  • What the reader sends when you omit it is not specified in the available sources.

Clean Session​

  • With cleanSession: true, the default, the broker discards any previous session for the client ID when the reader connects. Commands published while the reader was offline are not delivered to it later.
  • With cleanSession: false and a stable clientId, the broker keeps the session, including queued QoS 1 and 2 messages and subscriptions, so the reader can receive commands that were sent while it was offline.

Before you choose false, note that the reader carries out every command it receives. Commands that the broker queued while the reader was offline are carried out when it reconnects, however long it was away. See Duplicates and Retries.

Keep-Alive​

With a non-zero keepAlive, if the broker receives nothing from the reader for one and a half keep-alive intervals, the broker closes the connection and publishes the reader's Last Will. A keepAlive of 0 turns the keep-alive mechanism off.

Reconnect Delays​

reconnectDelayMin must be less than or equal to reconnectDelayMax. The schema cannot enforce this relation, so check it before you send the configuration. The published examples use the pairs 5/60, 10/120, 50/500, and 5/512; the last is also the pair in the reader's default endpoint configurations.

Credentials and Certificates​

mqttParams.username and mqttParams.password set the user name and password in the reader's CONNECT packet. The endpoint's securityParams names the installed certificates that the reader uses for TLS. See Authentication and Tenancy and TLS and Authentication.

Topics and QoS​

tenantId, mqttParams.publishTopics, and mqttParams.subscribeTopics set the topics for the endpoint, and qosCommon sets the endpoint's default QoS. See Topics and Channels and Delivery and Retry Semantics.

Parameters You Cannot Set​

ParameterStatus
MQTT protocol versionNo field. The contract declares MQTT 3.1.1.
Last Will message, QoS, and retain flagNo field. The Last Will topic is the endpoint's publishTopics[2], and the reader registers the Last Will itself; see Last Will.
TLS version and cipher suitesNo field. See TLS and Authentication.
