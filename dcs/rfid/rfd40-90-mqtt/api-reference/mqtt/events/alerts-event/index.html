alerts

Reference·Audience: API consumer·Use: interpret the reader's structured alert / notification events

Overview​

alerts is a device-emitted event that delivers structured, categorized alert information — the reader publishes it autonomously when a monitored condition changes state or crosses a threshold; no command triggers it. Each event is a fixed envelope (type, timestamp, state, id, priority) plus a category-specific alertDetails body selected by id. It is read-only telemetry and carries no credentials.

The same envelope carries two message classes, distinguished by type:

  • ALERT — an autonomous monitoring alert (battery, power, network).
  • NOTIFICATION — a command side-effect: FILE_DOWNLOAD (see install_certificate) and the FIRMWARE_UPDATE start (see set_os).

This page documents the full envelope and all seven alertDetails branch keys. config_events toggles (battery, power, network, firmwareUpdate, fileDownload) govern which alerts publish.

The id enum has five categories, all emitted on current V1.1 firmware: BATTERY, POWER, NETWORK_EVENT, FIRMWARE_UPDATE, and FILE_DOWNLOAD. The schema also declares a temperatureInfo branch, but there is no TEMPERATURE id and no temperature alert is emitted on current firmware. See What to Monitor and Why.

When to Use​

Subscribe to alerts when you want the reader to tell you about a monitored condition rather than asking for it — there is no command that returns this data on demand (no polling twin). Reach for it when you need to:

  • React to device-health changes as they happen — battery state and health (BATTERY), power-source and power-mode transitions (POWER), and network interface connect/disconnect (NETWORK_EVENT).
  • Track long-running command side-effects — the FIRMWARE_UPDATE stream during a set_os flash (a type: NOTIFICATION start, then in-progress notifications) and the FILE_DOWNLOAD result during an install_certificate transfer (type: NOTIFICATION), all on this same envelope.
  • Triage by severity — the priority field (CRITICAL … LOW) lets you route alerts without inspecting each branch body.

Enable only the categories you consume with config_events — a disabled category never publishes, so leaving one off is how you silence it. For a periodic health snapshot rather than change-driven alerts, use heartBeatEVT.

Topic Mapping​

alerts is device-emitted and flows on the management event topic — it has no cmnd/resp topics because no command produces it.

MessageDirectionTopicNote
EventReader → App<tenantId>/MGMT/clients/event/<serial>The same event topic that carries heartBeatEVT and NOTIFICATION-type events.

Topics follow the pattern <tenantId>/<topic>/<serial> — the tenant id assigned to you at provisioning (a slot you fill in, never a literal), the base topic you configure on the endpoint, and the reader's serial number, which the reader appends itself in its model-prefixed form (for example RFD40-212735201D0053). App → Reader means your app publishes and the reader subscribes; Reader → App means the reader publishes and your app subscribes.

See Topics and Channels.

Key Fields​

  • type (event) — message class: ALERT (autonomous monitoring alert), NOTIFICATION (command side-effect), or the reserved EVENT. Route on this to separate alerts from notifications.
  • timestamp (event) — ISO-8601 (format: date-time) instant the alert was generated.
  • state (event) — SET (condition active/asserted), CLEAR (resolved), or ONESHOT (one-time, no matching CLEAR). Pair with id to track a condition's lifecycle.
  • id (event) — the alert category (BATTERY, POWER, NETWORK_EVENT, FIRMWARE_UPDATE, FILE_DOWNLOAD); selects which alertDetails branch is populated.
  • priority (event) — severity, CRITICAL / HIGH / LOW, for triage without inspecting the branch body.
  • alertDetails (event) — the category-specific body (seven declared branch keys); exactly one branch is populated, matching id. Optional — not in the envelope required set.
  • config_events category toggles (request) — the emission gate: the per-category eventConfiguration flags (battery, power, network, firmwareUpdate, fileDownload) set with config_events govern whether each id publishes at all. A disabled category is silent.

state tells you whether a condition is active or resolved: SET = active/asserted, CLEAR = resolved, ONESHOT = a one-time event with no persistent state (it fires once and has no matching CLEAR). Every example on this page is ONESHOT, and so was every firmware-update notification recorded during one set_os run.

Event Semantics​

Emission​

The per-category eventConfiguration toggles you set with config_events govern which id categories publish: battery → BATTERY, power → POWER, network → NETWORK_EVENT, firmwareUpdate → FIRMWARE_UPDATE, and fileDownload → FILE_DOWNLOAD. A disabled category never publishes, so the absence of an alert is not proof of a healthy state. The FIRMWARE_UPDATE start and the FILE_DOWNLOAD result arrive as type: NOTIFICATION command side-effects (from set_os and install_certificate); the BATTERY / POWER / NETWORK_EVENT categories are autonomous type: ALERT events. The in-progress FIRMWARE_UPDATE events recorded during one set_os run were also NOTIFICATIONs. The config_events schema has a temperature toggle, but there is no TEMPERATURE id and no temperature alert is emitted, so enabling it has no effect.

Branches​

alertDetails declares seven branch keys and carries one of them; id selects the populated key. Two keys have no id value that selects them:

Field Support​

  • type distinguishes alerts from notifications. type: ALERT is an autonomous monitoring alert; type: NOTIFICATION is a command side-effect — FILE_DOWNLOAD (during install_certificate / firmware download) and the FIRMWARE_UPDATE start (during set_os). EVENT is in the enum but was not observed. All three share this one envelope.
  • FILE_DOWNLOAD fileName is the stored basename. downloadInfo.fileName is the name the reader stores internally — the URL basename stem (e.g. a source …/mqtt_ca_cert.pem yields fileName: "mqtt_ca_cert"), not your request name. Do not expect a 1:1 match to a get_installed_certificates entry name without the source URLs.
  • The interface key is interface on these items. Each ethStatus/wifiStatus item names its interface with the key interface ("interface": "eth0"), while the Wi-Fi and Ethernet commands and their read-backs use interfaceName for the same concept. The key is required: an ethStatus item requires interface, status, linkStatus and ipV4Address, a wifiStatus item interface, status, ssid and ipV4Address.
  • alertDetails is optional; envelope is required. The envelope required set is [type, timestamp, state, id, priority]; alertDetails is not required. Validate the envelope strictly.
  • batteryAlert.stateOfHealth is the same health grade as get_status. The value set here is GOOD / CRITICAL / MODERATE, and get_status reports deviceStatus.batteryStatus.stateOfHealth from that same enum. One grade, so nothing needs translating when you share battery logic between the command and the event stream. The battery's charge state is the separate status field. See Interpret stateOfHealth.

Examples​

Every contract example is in the Alert category dropdown under Event Payload, and all of them are the reader's own live captures. For the FIRMWARE_UPDATE category, the dropdown shows the NOTIFICATION that starts an update (from set_os); the in-progress notifications that follow are under set_os Progress. The two FILE_DOWNLOAD options come from an install_certificate transfer: one reports the download, the other the save.

Notes and Caveats​

  • Validate against the long-form alert, not the SOTI short form. Two alert shapes exist: the long-form envelope on this page (the one the reader publishes on the management event topic) and the short-form (SOTI) projection, a flat shape with granular ids like BATTERY_LOW_SET that carries neither state nor alertDetails and is reachable only on the SOTICONNECT endpoint — out of scope here. No id value is shared between the two vocabularies and no mapping between them is defined, so only the long form matches what the reader publishes here.
  • No response envelope. alerts is a device-emitted event, so it carries no response/code — the command response-code table does not apply, and no response code is defined for any event.

alerts is read-only telemetry with no credentials. Remember emission is gated by config_events (see Event Semantics). For the concept-level view, see Respond to Alerts and Configure Event Reporting.
